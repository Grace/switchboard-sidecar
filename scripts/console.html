The provider is a mock. The routing is not: a real gateway reads a real signed policy, really fails over, really retries, and really counts tokens. What is simulated is the answer — the mock returns canned text instead of calling OpenAI or Anthropic. That is also why you can watch a failover on the first click rather than waiting for somebody's outage.

Where this sits

the internet → your agent →127.0.0.1 switchboard → providers one task · keys never leave it

Switchboard is a sidecar: it runs beside your application in the same task or pod and listens on loopback only, so your agent reaches it at 127.0.0.1 and nothing else can. Your agent is the internet-facing part; the process holding the provider API keys never is. It is the same shape as Envoy, Linkerd or the OpenTelemetry collector.

One sidecar serves one tenant — the tenant is in its config and the routing policy it fetches is signed for that tenant. Loopback is how that is enforced today, which is why the gateway refuses to bind anything else: listen must be a loopback IP:port; use one sidecar per tenant.

Today that is the only shape. There is no endpoint to send your production traffic to: you deploy it, it runs next to your code, and the only thing leaving your task is the call to the provider you chose. Nobody is in the path of your prompts, including us.

Planned: a network-facing single-tenant deployment, so one gateway can serve a team rather than one per service — reached over mTLS, with the caller proven by certificate instead of by being on the same loopback interface. And a hosted option for people who would rather not run it at all. Neither exists yet, and the roadmap for both is in docs/GAPS.md with what each actually requires.
